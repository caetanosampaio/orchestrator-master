# Missions v2: criar missão por briefing (terminal planejador)

Decisões do usuário (2026-11-19, não reabrir): o briefing vira missão por um **terminal planejador** visível, como o Maestro do Cockpit; a proposta **abre no formulário para revisão** e só vira missão quando o usuário clica Criar (e depois Iniciar). Nada é criado nem iniciado sozinho.

## Fluxo
1. Em Missões, "Nova por briefing" → o usuário escolhe o workspace (padrão: o ativo) e, opcionalmente, o agente do planejador (Claude padrão; modelo/esforço das listas fechadas) → `POST /api/flows/briefing`.
2. O servidor abre um terminal com o papel `planner` no workspace (mesmo caminho de `terminals.create`; o pane tem o MCP do FORGE como todo pane). A tela mostra esse terminal na própria página de Missões.
3. O usuário escreve o briefing no terminal. O planejador lê o projeto (só leitura), pergunta o que faltar, consulta `mission_options` e envia a proposta com `propose_mission`. Se a validação recusar, recebe o erro em português e corrige.
4. A tela percebe a proposta pendente (`GET /api/flows/proposals`, polling junto com o de `/api/flows`) e abre o formulário de Nova missão PREENCHIDO, com o aviso "Proposta do planejador: revise antes de criar". Acesso total vem SEMPRE desligado (só o usuário liga).
5. O usuário ajusta e cria (`POST /api/flows` com `proposalId`) → a proposta vira `used`. Ou descarta (`POST /api/flows/proposals/:id/dismiss`). O terminal do planejador continua aberto para refinar (o usuário o fecha quando quiser); uma proposta nova do mesmo terminal substitui a pendente anterior.

## Contratos
**Papel `planner`** (server/terminals.js `ROLES`): label "Planejador", `edits` ausente (não edita), prompt próprio: "Você é o PLANEJADOR de missões do FORGE. Converse com o usuário para entender o objetivo, leia o projeto (sem editar arquivos nem rodar comandos que alterem algo), consulte mission_options e proponha a missão com propose_mission: etapas pequenas e verificáveis, papel certo para cada uma (Construtor edita; Revisor revisa; Batedor investiga), dependências só quando uma etapa precisa do resultado de outra, paralelo quando forem independentes, modelo/esforço proporcional à dificuldade (leve para tarefas simples, forte só para as difíceis). Cada prompt de etapa diz o resultado esperado e como saber que terminou. Se a validação recusar, corrija e envie de novo. Não inicie a missão: o usuário revisa e cria." `planner` NÃO é papel de etapa (flows.js `STEP_ROLES` exclui `maestro` e `planner`), não recebe tarefas do Maestro (maestro.dispatch/send_task recusam `planner` como destino, como já fazem com `maestro`). **Somente leitura imposta pela CLI** (terminals.js `READ_ONLY_ROLES` → `paneArgs({ readOnly: true })`, decidido pelo papel no servidor): Claude Code recebe `--disallowedTools Edit Write NotebookEdit` (no grupo final de argumentos, logo antes de `--mcp-config`/`--allowedTools`, para a lista variádica não engolir nada); Codex roda com `-s read-only -a on-request` no lugar de `-s workspace-write`. O planejador nunca recebe acesso total (`--dangerously-skip-permissions` / `--dangerously-bypass-approvals-and-sandbox`): nem pelo Maestro autônomo, nem por `fullAccess` interno, nem herdado. **Não entra em times** (terminals.js `TEAM_ROLES` = maestro, builder, reviewer, scout; team-templates.js recusa vaga `planner` com "O Planejador não entra em times: abra-o pela tela de Missões (Nova por briefing)." e a leitura tolerante descarta time gravado com ela); `GET /api/terminals` > `roles[]` ganhou `team: boolean` (false só no planner) para o cliente filtrar o seletor de papel do Cockpit e o editor de times.

**Ferramentas MCP** (server/maestro.js), só para o papel `planner` (`PLANNER_ONLY`; os demais papéis não as veem em tools/list e recebem erro se chamarem; o planner não vê as do maestro):
- `mission_options` → JSON (dado do servidor, confiável): `{ workspace: { name, git: boolean }, providers: [{ id, label, available, models: [{id,label}], efforts: [{id,label}] }], roles: [{ id, label, edits, what }], limits: { maxSteps, maxParallel, maxTitle, maxGoal, maxPrompt }, kinds: ['project','automation'], schedule: { kinds: ['interval','daily','weekly'], everyHours: [1,168], time: 'HH:MM', days: '0=dom..6=sáb' }, notes: [...] }`.
- `propose_mission` args `{ title, goal?, kind?, maxParallel?, schedule?, autoIntegrate?, steps: [...] }` (mesmo formato de `POST /api/flows`, SEM `workspaceId`, SEM `fullAccess` e SEM `accounts`: o workspace é o do pane; `fullAccess` é sempre `false`; a conta de cada provedor só o usuário escolhe no formulário (Contas v2, `PLANNER_DENIED_KEYS`); chave extra recusada). Valida com o MESMO `validateFlowInput` de flows.js. Se houver agenda (`schedule` não nulo), a proposta a guarda com `enabled: false`: só o usuário liga a agenda no formulário. O contexto do pane (workspace e papel) vem de `terminals.get` (describe), não do `peek`, que não traz `workspaceId`. Erro → `isError` com a mensagem. Ok → texto "Proposta <id> enviada para revisão na tela de Missões. O usuário vai revisar e criar; você pode continuar refinando e enviar outra (ela substitui esta)."
- O maestro.js não importa flows.js: recebe uma porta injetada depois do boot (`maestro.setPlanner({ options(caller), propose(caller, args) })`), ligada em `index.js` depois de `setupFlows`.

**Propostas** (server/flows.js, só em memória; somem no reinício): `{ id: 'prop_<8hex>', terminalId, workspaceId, createdAt, status: 'pending'|'used'|'dismissed', flow: <valor validado, fullAccess:false> }`; no máximo 1 pendente por terminal (a nova substitui), 20 no total, expiram em 24 h. Pendente de um planejador que **não está mais rodando** (fechado, terminou ou sumiu) vira `dismissed` com `dismissReason: 'terminal_closed'` na próxima varredura: sai de `GET /api/flows/proposals`, não conta no limite de 20 e o dismiss dela responde 404.

**Rotas** (origin-guard/token como as demais; `/api/flows/*` já está em PROTECTED_READ):
- `POST /api/flows/briefing` `{ workspaceId, provider?, model?, effort?, acknowledgeProjectConfig?, accountId? }` → 201 `{ terminalId, session }` (terminal role `planner`, título "Planejador de missão"); 400 validação (chave extra; `acknowledgeProjectConfig` que não seja booleano; `accountId` fora do formato `acc_<8hex>` = 400 `account_not_found`); **conta (Contas v2)**: `accountId` é a conta que o USUÁRIO escolheu para o terminal do planejador (ainda não há missão, então é a escolha feita no próprio briefing); ausente = a regra do `accounts.resolveFor` (a ÚNICA conta utilizável do provider); a recusa do `terminals.create` chega com o status e o `code` dele e `provider` (400 `account_not_found`/`account_provider_mismatch`, 409 `account_required` com 2+ contas do provider, `no_account`, `account_disconnected`, `account_missing`): o cliente mostra o seletor de conta desse provider e reenvia; 404 workspace; 409 limites de terminais/provedor indisponível (repassa o erro do terminals.create); 409 `{ error, code: "project_config_unreviewed", files: [{ path, why }] }` quando o workspace tem configuração executável não revisada: o cliente mostra os arquivos e, com a confirmação do usuário, reenvia com `acknowledgeProjectConfig: true` (mesmo comportamento do Cockpit; repassado ao `terminals.create`).
- `GET /api/flows/proposals` → `[{ id, terminalId, workspaceId, workspaceName, createdAt, flow }]` só `pending` e não expiradas.
- `POST /api/flows/proposals/:id/dismiss` → 204; 404.
- `POST /api/flows` aceita `proposalId` opcional (formato `prop_<8hex>`): se existir pendente, vira `used` depois da criação bem-sucedida; inexistente/expirada → a missão é criada normalmente (o id só serve para baixar a proposta).

**Histórico de terminais** (`GET /api/terminals/history`): sessões de papel `planner` saem com `resumable: false`, `reopenable: false` e `blockedReason: "planner_session"` (a restauração automática do Cockpit não as traz de volta); `POST /api/terminals/resume` de registro planner (retomar, `fork` ou `reopen`) → 409 `{ error: "Abra um novo planejador pela tela de Missões.", code: "planner_session" }`.

## Segurança
Proposta é texto de agente (não confiável): só vira missão por clique do usuário no formulário; `fullAccess` nunca vem do agente; workspace nunca vem do agente; limites e validação iguais aos de `POST /api/flows`. O planejador não edita arquivos: além da instrução do papel, a própria CLI bloqueia as ferramentas de edição (Claude: `--disallowedTools Edit Write NotebookEdit`; Codex: sandbox `read-only`) e ele nunca sobe com acesso total. A agenda de uma proposta vem sempre desligada. Limites: no Claude o `Bash` continua disponível (pedindo permissão, como em qualquer pane sem acesso total), então um comando de shell aprovado pelo usuário ainda pode alterar arquivos; no Codex, a hipótese (não verificada contra a CLI real) é que o sandbox restringe só os comandos e patches pedidos pelo modelo, e as chamadas MCP às ferramentas do FORGE, feitas pelo próprio processo do Codex, seguem funcionando.
