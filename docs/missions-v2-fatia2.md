# Missions v2, fatia 2: paralelo isolado, integração, retomada e agenda

Plano aprovado em 2026-11-19 (architect + decisões do usuário). Complementa `docs/missions-v2-spec.md` (fatia 1 e itens de 2026-11-19). Contrato para quem implementa; não reabrir as decisões.

## Decisões do usuário (fixas)
1. **Paralelo real**: run em workspace Git ganha a BRANCH DA MISSÃO `orch/run_xxxxxxxx` (criada do HEAD da branch do workspace, NUNCA em checkout). Cada etapa ganha worktree próprio criado da ponta atual dessa branch. Etapa concluída (report_done ou aceitação humana) → commit no worktree → integração AUTOMÁTICA na branch da missão (só plumbing: merge-tree/commit-tree/update-ref com CAS; nenhuma pasta de trabalho é tocada). Conflito → a missão não inicia etapas novas e espera o usuário. Dependentes só começam com as dependências integradas. A pasta do usuário não muda durante o run; alterações não commitadas nela não impedem o run (e não entram na missão). Workspace sem Git = modo pasta (comportamento atual, Construtores serializados por `editorActive`).
2. **Integração final**: run todo concluído e integrado → `merge --ff-only` (com commit de merge montado por commit-tree se não for fast-forward) na branch atual do workspace, AUTOMÁTICA se: sem conflito, pasta limpa, mesma branch-base, sem configuração executável/arquivo sensível alterado. Senão o run fica `ready_to_integrate` esperando Integrar (reconfere tudo) ou Descartar. Opção por missão `autoIntegrate` (padrão `true`, desligável). Registro auditável `integration.by = 'auto'|'user'` com digest + `store.log('flow', …)`.
3. **Agenda**: automação = missão `kind: 'automation'` com `schedule`; roda só com o servidor no ar; presets (a cada N horas; diário HH:MM; dias da semana HH:MM; fuso local). Horário perdido = pulado; run ativo no horário = pulado; pulos registrados. Nada roda no boot.
4. **Retomar**: reinício do servidor deixa o run `interrupted`; o usuário clica Retomar (nunca automático). Claude volta à conversa (`--resume`) e recebe "continue de onde parou"; Codex recomeça a etapa num terminal novo no mesmo worktree.

Padrões adotados pelo coordenador (o usuário pode mudar): sem preparação automática de dependências no worktree (a UI avisa que a cópia só traz arquivos versionados); depois da integração final bem-sucedida, fechar os terminais OCIOSOS do run e limpar worktrees/branch com as regras seguras (o que não puder sair vai para `leftovers`); sem limite de duração por automação; excluir missão com branch/worktrees é permitido (os registros em `db.worktrees` ficam, a trava de remoção do workspace continua); sem "apagar à força".

## A. Modelo de dados (compatível com o banco atual)
**Flow** (`db.flows[]`), novos:
- `schedule: null | { enabled: boolean, kind: 'interval', everyHours: 1..168 } | { enabled, kind: 'daily', time: 'HH:MM' } | { enabled, kind: 'weekly', days: [0..6] (0 = domingo; únicos, ordenados, ≥1), time: 'HH:MM' }`. Só com `kind === 'automation'`.
- `autoIntegrate: boolean` (padrão `true`; flow antigo sem o campo = `true`).
- `scheduleState` (só o servidor escreve): `{ anchorAt, nextRunAt|null, lastSlotAt|null, lastRunId|null, skips: [{ slotAt, reason: 'missed'|'active_run'|'start_failed'|'limit'|'archived'|'workspace_missing', message, count?, at }] }` (máx. 20 pulos).

**Run** (`db.flowRuns[]`):
- `status`: `running | interrupted | ready_to_integrate | completed | failed | cancelled | discarded`. `ACTIVE_RUN = {running, interrupted, ready_to_integrate}`: bloqueia editar (exceto schedule/autoIntegrate), excluir e iniciar outro run; a agenda pula.
- `trigger: 'manual'|'schedule'`, `scheduledFor: iso|null`, `interruptedAt`, `resumedAt`, `resumes: n`.
- `git: null` (runs antigos e modo pasta sem flowGit) ou `{ mode: 'pending'|'git'|'folder', fallbackReason, repoPath (interno, não sai na API), baseBranch, baseCommit, branch, tip, state: 'creating'|'ready', op: null|{ kind: 'final_integrate', at, oldHead, newCommit }, integration: null|{ by: 'auto'|'user', mode: 'ff'|'merge'|'already'|'empty', at, from, to, missionTip, digest, policy }, pending: null|{ reasons: [{code, message}], conflicts: [], files: [], checkedAt }, leftovers: [{ worktreeId, reason }], cleanedAt, branchDeleted, discardedAt }`.

**Etapa do run**: `status` ganha `interrupted` (só dentro de run `interrupted`); novos `interruptedFrom: 'running'|'waiting'`, `delivered: boolean`, `recordId` (de `session.recordId`, interno), `worktreeId`, `branch`, `commit`, `dispatchFrom` (âncora do `dispatchWaitMs`; ausente = `startedAt`), `attempt`, `resumeMode: 'continue'|'restart'|null`, `resumePending: boolean`, `integration: { state: 'none'|'pending'|'integrating'|'integrated'|'empty'|'conflict'|'blocked'|'error', from, to, conflicts: [], files: [], error, at }` (ausente = `'none'`), `discardedBy: 'user'`.

**Worktree** (`db.worktrees[]`): novo `flow: { runId, stepIds: [] }`; `missionId = runId` (fica fora de `terminalWorktrees`, que filtra `/^term_/`); `baseBranch` = branch da missão.

Poda de 200 runs: não poda run com `git.branch` não apagada nem com `leftovers` (se não houver outro candidato, poda e registra no log).

## B. API (erros `{ error, code? }` em português; rotas com Git usam asyncRoute)
- `POST /api/flows`: aceita `schedule` (400 se `kind !== 'automation'` ou formato inválido) e `autoIntegrate` (booleano estrito).
- `PATCH /api/flows/:id`: aceita `schedule`, `autoIntegrate`, `kind` (validados contra o resultado mesclado). PATCH só com `schedule`/`autoIntegrate` é aceito com run ativo; os demais campos seguem 409. Mudar a agenda recalcula `nextRunAt` a partir de agora.
- `GET /api/flows`: cada flow ganha `nextRunAt` e `scheduleSkips` (últimos 5); `activeRun` = run em ACTIVE_RUN. A visão do run esconde `ownedTerminalIds`, `recordId` e `repoPath`; o caminho do worktree só aparece na etapa com conflito.
- `POST /api/flows/:id/runs/:runId/resume` (corpo vazio): 200 run `running`; 404; 409 (não `interrupted`, workspace removido, provedor indisponível, faltam vagas de terminal, `busy`, branch da missão sumiu, Git sem resposta); 500 gravação (rollback).
- `POST /api/flows/:id/runs/:runId/integrate` `{ acknowledgeProjectConfig?: true }`: 200 run `completed`; 409 com `code`: `not_ready`, `target_dirty`, `target_branch_changed`, `conflict` (+`conflicts[]`), `project_config_changed` (+`files[]`, exige ack), `git_unknown`, `busy`; 500 estado inesperado (nada desfeito; continua `ready_to_integrate` com diagnóstico). Ponta já ancestral do HEAD = `mode: 'already'`.
- `POST /api/flows/:id/runs/:runId/discard` `{ deleteBranch?: boolean }`: `ready_to_integrate` → `discarded`; `cancelled`/`failed` mantêm o status e gravam `git.discardedAt`. Remove worktrees só pelas regras seguras do `cleanup()`; branch só com `deleteBranch: true`. 409 se não for modo git, já descartado ou ocupado.
- `POST /api/flows/:id/runs/:runId/cleanup`: run `completed` com `leftovers` refaz a limpeza segura.
- `POST /api/flows/:id/runs/:runId/steps/:stepId/integration` `{ action: 'retry'|'discard', acknowledgeProjectConfig?: true }`: só etapa com `integration.state` em `conflict|blocked|error` num run `running`. `retry` commita o que estiver sujo no worktree e integra de novo; `discard` → etapa `failed` com `discardedBy: 'user'`, dependentes pulados, run segue.
- `POST /api/flows/:id/runs`: sem mudança externa; interno `startRun(flowId, { trigger, scheduledFor })`; 409 com run em ACTIVE_RUN.
- `POST .../steps/:stepId/decision`: continua exigindo `running`.

## C. Módulos
- **`server/worktrees.js`** (só acréscimos; `integrate`/`assess`/`snapshot` e o gate estrito NÃO mudam): exportar `withRepoLock`, `repoKey`, `resolveRepo`, `GIT_IDENT`, `dirtyStateOf(dir)`, `probeHeadOf(dir)` (o manager delega). `create({ mission, workspace, from?: { branch, commit }, flow?: { runId, stepId } })`: com `from`, dentro do lock confere `refs/heads/<from.branch>` == `from.commit`, `worktree add -b orch/wt_x <path> <commit>`, grava `baseBranch = from.branch`, `baseCommit = from.commit`, `flow`; sem `from` idêntico ao atual. `commitFlowWork(id, { message })` (só registro com `flow`; aceita ready/in_use/finished sem op; `add -A` + `commit --no-verify` com IDENT; `{ head, committed }`). `fastForwardFlow(id, commit)` (só `flow`, limpo, `merge --ff-only`). `describe` inclui `flow`.
- **`server/flow-git.js`** (novo; argumentos fixos, nada do cliente; tudo dentro de `withRepoLock(repoKey(repoPath))`): `createFlowGit({ db, worktrees, runGit, now, uid })` com `probe(ws)` → `git|folder|unknown` (unknown = run falha, nunca cai na pasta); `createMissionBranch(run)` (`git branch` sem checkout); `stepWorktree(run, rs)`; `refreshForContinue(run, wtId)`; `commitStep`; `integrateStep(run, rs)` (recusa se a branch da missão estiver em checkout em algum worktree; guard de config executável/sensível → `blocked`; merge-tree; conflito → `conflict`; ancestral → `empty`; ff ou commit-tree; diário `integrating` gravado ANTES do `update-ref <novo> <pontaAntiga>`); `assessFinal(run)` e `integrateFinal(run, { by, ack })` (mesma sequência do `integrate()` do worktrees.js: pasta limpa, na baseBranch, guard sobre `baseCommit..ponta`, merge-tree/commit-tree, `run.git.op` gravado antes do `merge --ff-only --no-edit`, confere HEAD; digest sha256 de `[run.id, repoPath, baseBranch, alvo, ponta, mergeTree]`); `cleanupRun(run)`; `discard(run, { deleteBranch })`; `settle(run)` (concilia diários só pelo Git real).
  - Guard: arquivos de `CONFIG_FILES`/`CONFIG_DIRS` de `project-config.js` e nomes sensíveis (`.env*`, `*.pem`, `*.key`, `id_rsa*`) → `blocked`/`project_config_changed`; só passa com `acknowledgeProjectConfig: true` vindo de clique do usuário.
- **`server/flow-schedule.js`** (novo): puras `validateSchedule(raw, kind)`, `nextRunAt(schedule, fromMs, anchorMs)` (horário local via `new Date(y, m, d, h, mi)`), `describeSchedule`. `createFlowScheduler({ flows, now, setTimer, clearTimer, checkMs = 30_000, graceMs = 120_000, maxScheduledActive = 3 })`: temporizador periódico `unref`; slot atrasado além de `graceMs` = `missed`; run ativo / arquivada / workspace inexistente = pulo registrado; mais de `maxScheduledActive` runs de agenda simultâneos = `limit`; falha do `startRun` = `start_failed`; `lastSlotAt` impede disparo duplo; no boot um `nextRunAt` vencido vira UM pulo `missed` com `count` e o próximo é calculado de agora.
- **`server/flows.js`**: `createFlows({ ..., flowGit = null, scheduler deps })`; sem `flowGit` = comportamento atual. Mutex por run (`ops: Map`) para tick e rotas (409 `busy`). `advance`: (1) preparar Git (`git.mode 'pending'`); (2) `resumePending`; (3) integrações pendentes por `finishedAt`; depois iniciar etapas. Dependência pronta = `completed` e (modo pasta ou `integration` em `integrated|empty|none`). Etapa com integração `conflict|blocked|error` impede iniciar etapas novas (as ativas seguem). `editorActive` só no modo pasta. Fim em modo git → `integrateFinal(by: 'auto')` se `flow.autoIntegrate`, senão `ready_to_integrate` com `pending.reasons`. Depois de integrar: fecha terminais ociosos do run, `cleanupRun`, `leftovers`. Toda mutação com `apply()` + rollback; diário antes de efeito no Git (se não gravar, não executa); depois do efeito `rollback: false`.
- **`server/index.js`**: `setupFlows(app, { db, terminals, maestro, worktrees })`; cria `createFlowGit` e o agendador; `recover()` síncrono + `recoverGit()` assíncrono sem bloquear o boot; o agendador entra no `stop`.
- **`server/terminals.js`**: opção INTERNA `worktreeId` em `create` (só registro com `flow`, `worktreeProblem` nulo, recusa se outro terminal vivo usa o worktree, `inspectConfig` na pasta do worktree); a rota HTTP não repassa o campo.

## D. Retomada
- `recover()` (síncrono): run `running` → `interrupted` ("clique em Retomar"). Etapa `running`/`waiting` sem `unconfirmed` → `interrupted` com `interruptedFrom`, `delivered = !!taskId`, `taskId = null`, `agentBusy = false`. Etapa `waiting` com `unconfirmed` continua esperando a decisão (substitui a regra anterior que zerava `unconfirmed` no reinício). `pending` segue.
- `recoverGit()`: concilia `run.git.op` e etapas `integrating` pelo Git real (ref == `to` → `integrated`; == `from` → `pending`; senão `error`); `final_integrate` resolvido → `completed` ou `ready_to_integrate`.
- Rota `resume`: valida, `flowGit.settle`, confere a branch da missão, marca run `running`, etapas interrompidas `running` com `resumePending: true`, `dispatchFrom = now`.
- `resumeStep` em ordem: (1) Claude com `recordId` e `delivered` → `terminals.resume({ recordId })`, `resumeMode 'continue'`, texto "Etapa X (retomada após reinício do servidor): continue de onde parou; ao terminar chame report_done" (cleanLine/limite); (2) senão `terminals.resume({ recordId, reopen: true })` (terminal novo, mesmo worktree, mesmo papel e fullAccess), `resumeMode 'restart'`, texto original + "pode haver trabalho parcial desta etapa nesta pasta; confira com git status"; (3) senão `terminals.create` (modo git: com `worktreeId` se ainda utilizável, senão worktree novo da ponta, registrando a perda; modo pasta: na pasta). `project_config_unreviewed`/`session_active` → etapa `failed` com a mensagem (nunca enviar ack sozinho); `workspace_missing` → run `failed`; demais → próximo passo. Worktree `inconsistent`, com `op` ou Git sem resposta → etapa `failed` com motivo, sem apagar nada.

## E. Integração automática e a regra do projeto
O gate "conclusão só com `verified`" é do ciclo antigo e de `worktrees.integrate()` e continua intacto. Na v2 a conclusão de etapa segue estrita (report_done ou aceitação humana). A integração na branch do usuário é um ato separado, autorizado pela política explícita da missão (`autoIntegrate`, decisão do usuário, desligável), registrada com `by: 'auto'`, digest e log. Nunca integra sozinha com: conflito, pasta suja, branch diferente, Git sem resposta, config executável/arquivo sensível alterado.

- FlowHeader: `interrupted` → Retomar + Cancelar; `ready_to_integrate` → Integrar + Descartar (confirmação, caixa "apagar também a branch"); `cancelled`/`failed` com Git → Limpar cópias; chips "branch orch/run_x", "integração automática", "próxima: 19/11 14:00".
- FlowAttention: conflito, interrupção e "pronta para integrar" com motivos (pasta suja, branch trocada, configuração alterada → exige confirmação explícita).
- FlowSidePanel: branch/worktree da etapa, estado da integração, arquivos em conflito, caminho do worktree com instrução, "Tentar de novo" / "Descartar etapa", "Abrir terminal".
- FlowForm: tipo (projeto/automação); agenda com presets; avisos "roda só com o FORGE aberto; horários perdidos são pulados" e, sem acesso total, "pode parar pedindo permissão sem ninguém olhando"; caixa "Integrar automaticamente quando terminar sem conflitos" (marcada); aviso de que alterações não commitadas na pasta não entram e que a cópia só traz arquivos versionados.
- FlowRuns: gatilho, integração (auto/usuário, commit), pulos de agenda. FlowWorkflow: selo de integração por nó; Entrega mostra "integrada em <branch>" ou "pronta para integrar".
